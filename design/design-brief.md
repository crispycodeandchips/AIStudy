# 디자인 브리프 — 웨딩페어 랜딩 & 신청자 관리

작성일: 2026-11-08 (같은 날 미정 항목 기획 반영)
근거: `.moai/project/product.md`, `.moai/project/structure.md`, `.moai/project/interview.md`, 2026-11-08 디자인 범위 문답, MoAI 기획 에이전트 결정안(사용자가 결정을 위임함)
함께 쓰는 문서: [claude-design-prompt.md](claude-design-prompt.md) (이 브리프를 Claude Design 지시문으로 옮긴 것)

표시 규칙
- **[운영자 입력]**: 실제 사업 정보라 운영자가 Payload CMS에 넣는 값이다. 시안에서는 자리 표시로 둔다.
- **[법률 검토 필요]**: 법률 검토 전에는 확정하지 않는다.

## 목표

웨딩페어 광고를 보고 들어온 예비 신랑신부가 박람회 정보를 확인하고 이탈 없이 참가 신청을 마치게 한다. 운영자는 신청 현황을 한 화면에서 파악한 뒤 Payload 관리자 화면에서 신청자를 관리한다.

근거: 프로젝트 목표가 "방문 신청을 랜딩페이지에서 빠짐없이 받고, 관리자가 신청자를 확인·분류·내보낸다"이다(`product.md`). 전환율 같은 성과 수치는 아직 없으므로 목표치는 정하지 않는다.

## 대상과 사용 맥락

| 사용자 | 확인된 사실 | 미정·가정 |
|---|---|---|
| 방문자 | 예비 신랑신부. 회원가입 없이 신청한다. | 유입 채널과 연령대는 확인되지 않았다. 광고 유입을 가정한다. |
| 관리자 | 운영자 1인. 역할 구분이 없는 Payload 관리자 계정 하나를 쓴다. | 하루 신청 규모는 모른다. |

- 기기: 방문자 화면은 **PC 우선(1440px)으로 만들고 모바일(390px) 버전을 함께** 만든다. 관리자 현황판은 PC만 만든다.
- 광고 유입이 많으면 모바일 비중이 클 수 있다. 그래서 모바일 하단 고정 신청 버튼을 둔다.

## 필요한 화면·산출물

| 화면 | 목적 | 핵심 콘텐츠 | 함께 그릴 상태 |
|---|---|---|---|
| 1a. 기본 랜딩 (`/`) | 박람회 전체를 알리고 회차를 고르게 한다 | 헤더, 기본 히어로(공통 문구), 회차 카드 목록, 참가 혜택, 참여 분야, FAQ, 신청 폼 섹션, 푸터 | 신청 가능한 회차가 없을 때 |
| 1b. 회차 랜딩 (`/fairs/[slug]`) | 광고 유입용. 특정 회차로 바로 신청하게 한다 | 회차 히어로(회차 이름·날짜·장소), 혜택(회차 값 우선), 오시는 길, FAQ, 신청 폼(회차 미리 선택) | 회차 종료·비공개일 때 |
| 2. 참가 신청 폼 (랜딩 안 `#apply` 섹션) | 신청 정보를 빠짐없이, 부담 없이 받는다 | 아래 "신청 폼 항목" 표 | 입력 오류, 제출 중, 서버 오류(입력값 유지) |
| 3. 신청 완료 (`/apply/complete`) | 접수됐음을 확인시킨다 | 접수 메시지, 신청 내용 요약, 오시는 길, 처음으로 | 요약 없는 기본 상태(새로고침·직접 접근) |
| 4. 개인정보 처리방침 | 처리방침을 공개한다 | 처리방침 본문 [운영자 입력] [법률 검토 필요], 운영자 정보 | 없음 |
| 5. 관리자 신청 현황판 (Payload 안) | 회차별 상황을 한눈에 본다 | 회차 선택, 상태별 신청 수(신규·연락 완료·방문 확정·방문 완료·취소), 중복 수, 유입 경로(UTM) 상위, 최근 신청 10건(휴대폰 가림), CSV 내려받기 | 데이터 없음 |

추가 산출물: 방문자 화면 디자인 토큰(아래 "브랜드" 표)과 기본 컴포넌트(버튼, 입력칸, 선택 목록, 체크박스, 칩, 아코디언, 카드, 하단 고정 버튼 바)의 상태별 시안(기본·hover·focus·오류·비활성).

제외: 신청자 목록·상세·회차 편집 화면은 Payload 기본 화면을 쓴다. 지도 임베드, 참가 업체 목록은 v1에 넣지 않는다.

### 신청 폼 항목

| 항목 | 필수 | 입력 형태 |
|---|---|---|
| 회차 | 필수 | 선택 목록. 신청 가능한 회차가 하나면 자동 선택하고 숨김. 회차 랜딩에서는 미리 선택 |
| 이름 | 필수 | 텍스트 |
| 휴대폰 번호 | 필수 | 숫자 키패드, 010-0000-0000 형식 안내 |
| 희망 방문 날짜 | 필수 | 선택한 회차의 개최일 중 선택. 하루짜리 회차는 자동 입력 후 숨김 |
| 희망 방문 시간대 | 선택 | 회차별 시간대 목록 중 선택. 고르지 않으면 "미정" |
| 예식 예정일 | 선택 | 날짜 선택 + "아직 미정" 체크 |
| 예식 지역 | 선택 | 시·도 17개 + 미정 |
| 방문 인원(본인 포함) | 선택 | 1명 / 2명 / 3명 / 4명 이상, 기본값 2명 |
| 신랑/신부 구분 | 선택 | 신랑 / 신부 |
| 관심 분야 | 선택 | 복수 선택 칩: 웨딩홀, 스드메, 혼수·가전, 예물, 허니문, 기타 |
| 개인정보 수집·이용 동의 | 필수 | "전문 보기" 아코디언 + 체크박스(미리 체크하지 않음) |

필수 항목은 라벨 옆에 "필수" 글자로 표시한다. 색만으로 구분하지 않는다.

## 브랜드와 참고 자료

- 제공된 브랜드 자료: 없다. 아래 값은 기획 단계의 제안이며 시안의 출발점이다.
- 시안용 가칭: **들꽃 웨딩페어 [가칭]**. 같은 이름의 상호·상표가 있는지 확인하지 않았으므로 시안에서만 쓴다.
- 로고: 글자 로고(워드마크). Noto Serif KR 600, 색은 `--color-primary`. 장식이 필요하면 선으로 그린 잎 하나만 둔다. 헤더 로고 자리 높이는 PC 32px, 모바일 28px로 정해서 실제 로고로 바꾸기 쉽게 한다.
- 분위기: 내추럴. 세이지 그린과 베이지, 꽃·식물 요소, 야외·스몰웨딩 느낌. 장식은 절제한다.
- 관리자 현황판은 방문자 브랜드를 따르지 않고 Payload 관리자 화면의 기본 스타일을 따른다.
- 참고 URL·이미지: 없다.

### 글꼴과 크기

- 본문·UI: **Pretendard** (SIL OFL). 400 본문, 500 라벨, 600 버튼, 700 강조. 자체 호스팅(`next/font/local`).
- 제목: **Noto Serif KR** (SIL OFL). 600 섹션 제목, 700 히어로 제목. 빌드 시 받아 자체 호스팅(`next/font/google`).
- 크기: 본문 16px / 행간 1.7, 보조 문구 14px 이상, 히어로 제목 PC 48px·모바일 32px, 섹션 제목 PC 32px·모바일 24px.
- 모서리: 입력칸 8px, 카드 12px, 칩 999px. 간격은 4px 단위. 그림자는 카드에만 연하게 한 단계.

## 콘텐츠 구성 결정

### 랜딩 콘텐츠 단위: 공통 + 회차별 덮어쓰기

| 위치 | 내용 |
|---|---|
| 공통 (`LandingPage` global) | 기본 헤드라인, 기본 소개 문구, 기본 배너, 기본 혜택 목록, 참여 분야 소개, FAQ, 푸터 정보 |
| 회차 (`Fairs`) | 이름, slug, 시작일·종료일, 장소명, 주소, 오시는 길 안내, 시간대 목록, 공개 상태 |
| 회차 덮어쓰기 (선택) | 히어로 헤드라인, 히어로 이미지, 혜택 목록 |

- 회차에 값이 있으면 회차 값을, 비어 있으면 공통 값을 쓴다.
- 혜택 목록은 공통 목록에 더하지 않고 **목록 전체를 바꾼다**. FAQ는 덮어쓰지 않는다.
- 회차 노출 조건: 공개 상태이고 종료일이 오늘 이후(KST)인 회차.

### 참가 혜택 카드

| 필드 | 형식 |
|---|---|
| 아이콘 | 정해진 6종 중 선택: gift / ring / calendar / sparkle / leaf / ticket |
| 제목 | 20자 이내, 필수 |
| 설명 | 60자 이내, 필수 |
| 조건 | 40자 이내, 선택 (예: "현장 계약 시") |

PC 3~4열, 모바일 1열로 배치한다. 시안 예시는 `[예시] 방문 기념품`, `[예시] 현장 계약 혜택`, `[예시] 상담 우선 안내`, `[예시] 경품 추첨`이다. 수량·금액·할인율·"선착순 N명" 같은 숫자는 넣지 않는다. 실제 혜택은 [운영자 입력]이다.

### 시간대 기본값

새 회차를 만들면 시간대 4개가 기본으로 들어가고, 운영자가 회차마다 고칠 수 있다: 11:00–13:00, 13:00–15:00, 15:00–17:00, 17:00–19:00. 실제 운영 시간은 [운영자 입력]이다.

### 신청 폼 위치와 이동

- 신청 폼은 랜딩페이지 안의 `#apply` 섹션에 둔다. 모달이나 별도 페이지는 쓰지 않는다.
- PC: 헤더 오른쪽에 "참가 신청하기" 버튼을 고정한다. 히어로 버튼과 회차 카드 버튼은 폼으로 스크롤하고, 첫 입력칸으로 초점을 옮긴다. 회차 카드 버튼은 그 회차를 미리 선택한다.
- 모바일: 화면 아래에 높이 56px 이상인 "참가 신청하기" 버튼 바를 고정한다. 폼 섹션이 보이면 숨기고, 페이지 하단에 같은 높이의 여백을 둔다.
- 완료 화면의 신청 요약은 제출 직후에만 보여 준다. 주소(URL)에 개인정보를 남기지 않는다.

### 오시는 길

주소, 안내 문구, "네이버 지도에서 보기"·"카카오맵에서 보기" 링크만 둔다. 지도 임베드는 외부 서비스라 넣지 않는다.

## 개인정보 동의

- 보유 기간 제안: **해당 회차 종료일로부터 3개월** [법률 검토 필요]
- 동의문은 버전을 붙여 관리하고, 신청마다 동의 시각과 동의한 버전을 저장한다.
- 수집한 정보는 참가 업체를 포함한 제3자에게 제공하지 않는다. 업체에 정보를 넘길 계획이 생기면 별도 동의가 필요하므로 동의문과 폼을 다시 정해야 한다.

### 동의문 초안 [법률 검토 필요]

법적 요건을 충족한다고 보장하지 않는 초안이다. 개인정보 보호법 제15조가 알리도록 정한 네 가지(목적, 항목, 보유·이용 기간, 거부 권리와 불이익)에 맞춰 구성했다.

> **개인정보 수집·이용 동의 (필수)**
>
> [운영자 상호]는 웨딩페어 방문 신청을 받기 위해 아래와 같이 개인정보를 수집·이용합니다.
>
> **1. 수집·이용 목적**
> 웨딩페어 방문 신청 접수, 신청자 본인 확인, 방문 일정 확인과 안내를 위한 연락, 방문 관련 문의 응대, 중복 신청 확인
>
> **2. 수집 항목**
> - 필수: 이름, 휴대폰 번호, 신청 회차, 희망 방문 날짜
> - 선택: 예식 예정일, 예식 지역, 희망 방문 시간대, 방문 인원, 신랑·신부 구분, 관심 분야
> - 자동 수집: 신청 일시, 유입 경로 정보(광고 매체·캠페인 구분 값)
>
> **3. 보유·이용 기간**
> 신청한 회차의 종료일로부터 3개월간 보관한 뒤 지체 없이 파기합니다. 다른 법령에 따라 보관해야 하는 경우에는 그 기간 동안 보관합니다.
>
> **4. 동의를 거부할 권리와 불이익**
> 동의를 거부하실 수 있습니다. 다만 필수 항목 수집·이용에 동의하지 않으시면 방문 신청을 할 수 없습니다. 선택 항목은 입력하지 않으셔도 신청할 수 있습니다.
>
> 수집한 개인정보는 위 목적 외의 용도로 이용하지 않으며, 참가 업체를 포함한 제3자에게 제공하지 않습니다.

법률 검토 때 함께 확인할 것: 보유 기간 3개월, "다른 법령에 따라 보관" 문구의 필요 여부, 유입 경로 정보를 수집 항목에 적어야 하는지, 처리방침 페이지 문구.

## 제약과 검토 기준

**기술**
- 구현: Next.js(React) + Payload CMS 3 계열.
- 스타일: **CSS Modules + 전역 CSS 변수 토큰 파일**. Tailwind는 쓰지 않는다. 토큰 파일은 방문자 화면 레이아웃에서만 불러와 관리자 화면 스타일과 섞이지 않게 한다. Claude Design 결과는 CSS 변수와 컴포넌트별 CSS 형태로 받는다.
- 관리자 현황판은 Payload 관리자 화면의 자체 스타일을 따른다.

**접근성 (목표)**
- WCAG 2.2 AA 수준을 목표로 한다.
- 텍스트 대비는 4.5:1 이상, 입력칸 테두리·초점 링은 3:1 이상으로 한다. 토큰 조합은 위에서 계산해 확인했다.
- 모든 입력칸에 보이는 라벨을 단다.
- 키보드만으로 신청을 끝낼 수 있게 한다.
- 상태를 색만으로 구분하지 않는다.
- 실제 화면의 대비·키보드 조작은 디자인 결과와 구현 결과에서 따로 점검한다.

**문구**
- 해요체 존댓말을 쓰고, 과장 광고 표현은 쓰지 않는다.
- 알림을 보내지 않으므로 "문자로 안내드려요" 같은 약속을 하지 않는다.

**개인정보**
- 관리자 표와 현황판의 휴대폰 번호는 가운데를 가린다(예: 010-****-1234).
- CSV에는 전체 번호가 들어가므로, 내려받은 파일의 관리 책임을 운영 문서에 적는다.
- 보유 기간이 지나면 v1에서도 운영자가 직접 파기해야 한다. Payload 관리자 화면에서 회차별로 걸러 한꺼번에 삭제하는 절차를 구현 단계에서 확인하고 문서로 남긴다.

**제외 범위**
마케팅 수신 동의, 회원가입·로그인, 결제, 시간대 정원(마감 표시), 지도 임베드, 참가 업체 목록, 제3자 제공.

**검토 기준** (시안을 받으면 확인한다)
1. 첫 화면에서 "언제·어디서·어떻게 신청하는지"가 바로 보이는가
2. 모바일 하단 고정 버튼이 늘 보이고, 폼 섹션에서는 사라지는가
3. 필수 5개와 선택 항목이 글자로 구분되는가
4. 오류 문구가 해당 항목 바로 아래에 나오는가
5. 지어낸 숫자나 확정되지 않은 약속 문구가 없는가 (`design-slop-check`로 검토)
6. 현황판이 Payload 기본 화면과 어색하지 않게 어울리는가
7. 기본 랜딩과 회차 랜딩의 히어로 차이가 분명한가
